# R2 Character-First Temporal Engine

Status: **ACTIVE R2 SPECULATIVE-DEVELOPMENT DOCTRINE**

Location: `r2/editorial/character-rebuild/TEMPORAL_ENGINE.md`

Primary calibration: the character-first horizon experiments, the completed one-year Black Stair temporal experiment, connected high-fidelity audits, and the active `r2/FUTURE_SURVIVOR_PROTOCOL.md`.

## Purpose

Use fictional time deliberately.

The Temporal Engine exists to explore enough future story for accumulation, consequences, relationships, capability, money, work, geography, magic, reputation, and ordinary life to change without allowing a speculative future to become a railroad.

> **Temporal leverage may increase search depth. It may not lower the character bar.**

The engine is now active doctrine on `main`. That activates the **method**, not any speculative future.

## Authority boundary

Accepted R2 Story State and selected accepted prose on current `main` remain story authority.

A temporal run is experimental by default even when it is coherent, complete, polished, dated, chapter-sized, or emotionally satisfying.

No temporal experiment may directly overwrite accepted story truth, public chapter order, reader routes, registry/data, audio, or image authority merely because the experiment finished.

Useful future material must still survive the normal R2 process in `r2/FUTURE_SURVIVOR_PROTOCOL.md`: reconcile against current authority, classify, re-perform where needed, and select through the normal production path.

Historical later R2 and older temporal experiments are quarry/challenger evidence, not automatic chronology.

## The Temporal Run Contract

Every substantial temporal run must own a compact run contract before it expands.

Use `TEMPORAL_RUN_TEMPLATE.md` for the durable shape.

A valid run contract contains:

1. **AUTHORITY ANCHOR** — the current accepted R2 authority the experiment begins from.
2. **CLOCK** — how much fictional time this run is responsible for exploring.
3. **AT LEAST ONE CONSTRAINT** — one meaningful hard constraint or soft nudge that gives the run pressure beyond simply passing time.
4. **STOP CONDITION** — what ends this run or causes it to pause for reconciliation.
5. **OPTIONAL OUTPUT/FIDELITY TARGET** — chapter count, prose mass, confidence-zone depth, or similar production shape when useful.

Do not create a giant permanent simulation ledger merely because the contract exists.

The run contract should be small enough that a fresh worker can read it in one pass and continue without chat archaeology.

## Clock: time is a first-class input

A temporal run must know what fictional time it owns.

Accepted clock shapes include:

- exact elapsed duration: `10 days`, `six weeks`, `one season`, `one year`;
- an in-world target date or deadline;
- event-relative time: `until the expedition leaves`, `through the winter`, `until the theatre closes`;
- a bounded chapter/time combination when the user explicitly asks for both;
- a high-confidence inferred horizon from the user's nudge and current context.

The clock does **not** require inventing a complete canon calendar.

Use the cheapest time representation that preserves continuity: day counts, relative dates, seasonal labels, known in-world dates, or explicit elapsed-time markers.

### Clock resolution order

Resolve time in this order:

1. **Explicit current user instruction.**
2. **Already-established active run contract.**
3. **High-confidence inference from the current nudge, current authority, and immediate task.**
4. **One concise clarification question only when unresolved ambiguity would materially change the run.**

Do not ask the user to repeat a horizon that is already obvious.

Examples:

- `do a year` -> clock becomes one year.
- `do winter` -> clock becomes the relevant winter span unless current authority makes that ambiguous.
- `keep going` -> preserve the current clock and remaining stop condition.
- `continue this for another month` -> extend or replace the current clock by one month according to the current run state.

If the user says `continue` and a durable run contract exists, continue it. Do not reopen setup questions merely because a new worker entered the conversation.

## Time must leave residue

Date labels are not enough.

Elapsed time should change the world in ways the reader can feel.

Relevant residue includes, when earned:

- body, soreness, injury, recovery, conditioning, age, sleep;
- weather, season, daylight, roads, rivers, ecology;
- money earned, spent, saved, lost, borrowed, owed;
- work shifts, customers, contracts, rehearsals, jobs, competence;
- relationships, availability, grudges, intimacy, jokes, habits, expectations;
- household routine, food, clothing, repairs, objects, gear;
- rank, reputation, social position, permissions;
- geography, routes, travel knowledge, recurring places;
- letters, messages, absences, missed events, off-page decisions;
- magic practice, evidence, technique, cost, tools;
- obligations that appeared while Greg was elsewhere.

For an intentional gap greater than roughly two days, the next lived phase should **normally** establish at least two concrete consequences of elapsed time before the new action fully settles.

This is a diagnostic default, not a prose quota.

Do not write `three weeks passed` and then reset everyone to the same emotional, financial, bodily, and social state.

Do not force every domain to change every time. The point is credible accumulation, not ledger completion.

### Long-horizon check

For a run measured in months or a year, periodically ask:

- Does the beginning feel materially earlier than the current point?
- Have people other than Greg changed while he was absent or busy?
- Has ordinary life accumulated instead of merely plot events?
- Have money, gear, routes, relationships, capability, or obligations moved enough to prove time existed?
- Is the story still producing scenes, or has it collapsed into seasonal synopsis?

If the run feels like forty consecutive mornings wearing different date labels, the clock has failed.

## Constraint: every run needs pressure

A temporal horizon by itself is not an experiment question.

Every run must carry at least one meaningful **hard constraint** or **soft nudge** besides the clock.

If the user explicitly supplies one, use it.

If the user does not, infer one from the purpose of the current request when confidence is high. Ask one concise question only when no meaningful constraint can be inferred without materially changing the experiment.

### Hard constraints

Hard constraints are pass/fail.

Treat these as hard by default:

- explicit deadlines;
- explicit counts or thresholds;
- `must`, `must not`, `do not`, `at least`, `no more than`;
- required appearances or events;
- explicit rank/progression ceilings;
- explicit location or time boundaries;
- protected uncertainty or canon ceilings.

Examples:

- `A meaningful Gold-caliber party must appear during the run.`
- `Greg does not become Gold during this year.`
- `The run remains in Carrow.`
- `The expedition must leave before the final month.`
- `No chosen-one resolution.`
- `At least one relationship problem must remain unresolved at the end.`

Hard constraints shape possibility. They do not dictate exact scenes unless the user did.

### Soft nudges

Soft nudges change selection pressure and flavor.

Examples:

- more action;
- a little more fantasy/isekai trope pleasure;
- more romance;
- less work;
- more travel;
- messier people;
- let Greg look cool sometimes;
- more ordinary-life texture;
- stronger party dynamics;
- fewer institutional scenes.

A soft nudge is **not** a hidden quota.

`More action` does not mean every chapter needs a fight.

`More tropes` does not mean the world suddenly acquires stat screens.

`More romance` does not mean every interaction exists to service a relationship arc.

## Natural-language nudges are valid engine control

The user should not need to write a formal run specification.

Treat conversational nudges as legitimate updates to the active run contract.

Examples:

- `a year` -> set or replace the clock with a one-year horizon.
- `Gold party` -> add a meaningful Gold-party constraint or pressure at the smallest scope consistent with the request.
- `more action` -> increase action-selection pressure.
- `a little more tropes` -> permit more recognizable fantasy/isekai pleasures while preserving R2 identity.
- `don't make Greg Gold yet` -> add a hard progression ceiling.
- `make the next season more domestic` -> apply a seasonal soft nudge without rewriting the entire run.
- `continue` -> preserve the existing contract and advance from current durable state.

### Nudge update rule

New nudges modify the current contract unless they clearly start a new experiment.

Record only nudges that materially change future selection. Do not preserve conversational chatter as permanent state.

Explicit newer user direction outranks older soft nudges.

If two hard constraints conflict, stop and resolve the conflict rather than silently choosing one.

A nudge is run-local unless the user explicitly promotes it to durable project doctrine.

## Word count is not the clock

Time and prose mass are separate.

A run may use chapter-count or word-count targets to encourage full rehearsal, but word count does not prove that time passed and does not prove that a scene was lived.

Unless the user explicitly makes word count a hard requirement:

- treat it as fidelity evidence, not success by itself;
- challenge under-length material for missing lived phases, aftermath, waiting, failed attempts, physical environment, social friction, travel, relationship residue, or ordinary life;
- do not pad by restating conclusions;
- allow a shorter complete scene to survive when it genuinely wins;
- prefer more **life per word** over arbitrary mass.

A long chapter can still be treatment-like. A short chapter can still be complete.

## Confidence horizons

The existing A/B/C/D system remains useful, but it answers **confidence/fidelity**, not elapsed time.

Do not confuse the time clock with the confidence horizon.

### A — current hard run

- directly adjacent to accepted authority;
- full Shared Greg Surface fidelity;
- fresh exact read before writing;
- connected reader/challenger pass before acceptance;
- branch completion does not mean publication.

### B — next hard run

- high-fidelity scene/chapter-equivalent material;
- real production but replaceable;
- must obey accepted A facts;
- promotion requires fresh re-performance against newest A.

### C — warm rehearsal

- scene-complete or compressed future material depending on what improves judgment;
- preserve wants, decisions, residue, money, work, body, geography, magic, objects, and obligations;
- exact chronology may remain softer unless the run clock requires precision.

### D — cold rehearsal

- cheap far-edge reconnaissance only when a real contrast, pressure, or hinge exists;
- robust possibilities over brittle facts;
- empty D is healthy;
- no quota and no false far-future authority.

A one-year run may contain A/B/C/D confidence zones while still using one continuous time clock.

## Planner / renderer firewall

The year experiment showed that a coherent story can still sound broken when the prose renderer starts repeating the planner's rubric.

The fix is architectural separation.

### Planner may see

The planner, state manager, and scrubber may read:

- this full Temporal Engine;
- the active Temporal Run Contract;
- Future Survivor doctrine;
- anti-pattern files;
- confidence labels;
- experiment history;
- old quarry;
- audits and challenger verdicts;
- hard and soft constraints;
- long-range clocks.

### Renderer should see less

Before writing reader-facing prose, reduce planning state into a compact **Scene Packet**.

The Scene Packet should contain only concrete scene-relevant information:

- current fictional time and elapsed gap;
- location and physical situation;
- concrete state changes since the last lived scene;
- people present and what each wants now;
- active task, pressure, desire, interruption, or problem;
- one or two run constraints materially relevant to this scene;
- facts that may not be contradicted;
- consequences that should survive the scene.

It should **not** contain the whole engine constitution.

### Prose contamination rule

Story prose must not expose planning machinery merely because the planner uses it.

Reject or rewrite accidental references to:

- horizon architecture;
- rehearsal status;
- quarry or alternate versions;
- canon/authority labels;
- run constraints as author-side concepts;
- generator/model/writer instructions;
- audit verdicts;
- survivor labels;
- explanations that a scene is avoiding a trope because the engine told it to.

A word may still appear when it independently belongs naturally in the fictional world. The prohibition is against meta leakage, not vocabulary policing.

The post-render scrubber sees the full doctrine again and removes leakage, repeated evaluator fragments, thesis lines, and other long-run renderer residue.

## Character-first survivor gate

Causal survival is necessary but not enough.

Before material can promote toward A/B, ask:

1. What does each established person want now?
2. What are they doing when Greg is absent?
3. What does Greg notice first?
4. What is he avoiding noticing?
5. What does he get wrong specifically because he is Greg?
6. What does another person choose that Greg does not own?
7. What does this scene discover that another competent-work scene could not reveal as well?
8. Strip names and obvious biography: are the people still identifiable?
9. Does useful social/emotional/material residue survive the scene?
10. Is the scene shape earned by these people, or merely familiar to the generator?

If an event survives but the scene fails this gate, preserve the discovery and re-perform later.

## Independent clocks inside the run

The primary run clock answers **how far through fictional time the experiment travels**.

Independent character/world clocks answer **what continues changing during that time**.

Track only clocks materially relevant to the active run.

Possible clocks include:

- Greg: body, money, magic, work, home, desire, obligations;
- partner/friend/family: work, availability, ambition, intimacy, resentment, independent relationships;
- recurring workers: shifts, money, competence, customers, injuries, jobs, favors;
- institutions: work availability, rules, staffing, route conditions, reputation;
- setting: weather, roads, river, market, theatre schedule, repairs, local ecology.

Only instantiate clocks supported by current accepted authority or freshly established inside the experiment.

Do not import a named person, relationship, event, or state merely because an older rehearsal used it.

Do not build a permanent simulation ledger for people who are not relevant to the current run.

## Scene advancement

A meaningful future scene changes at least one:

- desire;
- attachment;
- resentment;
- misunderstanding;
- trust;
- expectation;
- money;
- body;
- capability;
- responsibility;
- belonging;
- reputation;
- geography;
- home;
- work ownership;
- magic understanding;
- relationship language;
- self-story.

Procedure alone does not earn a chapter.

Procedure may earn a chapter when it creates distinctive human discovery, choice, pleasure, cost, tension, comedy, competence, or consequence.

## Greg friction gate

Do not optimize Greg into perfect restraint.

Allow earned vanity, jealousy, desire, loneliness, avoidance, overattachment, premature grief, defensiveness, social mistakes, control disguised as advice, resentment toward defensible choices, and technically correct behavior that still lands badly.

No flaw quota.

The run contract may increase conventional fantasy pleasure without requiring Greg to become socially, professionally, or emotionally optimized at the same speed as his capability.

## Power / trope pleasure gate

Recognizable fantasy pleasures are tools, not contamination.

When the run calls for more genre pleasure, useful shapes may include:

- ranks and better contracts;
- ruins and old magical sites;
- monsters and materials;
- rare equipment and loot;
- party composition and role ownership;
- visible technique growth;
- status mismatch;
- increasingly dangerous roads;
- specialists recognizing unusual capability;
- decisive victories that are allowed to feel good;
- stronger teams whose competence appears through judgment, coordination, restraint, and role clarity rather than only larger damage.

Do not import game UI, stat screens, menus, or chosen-one logic unless accepted R2 authority independently establishes them.

Do not reflexively sabotage every competence beat to prove the story is character-first.

## Connected-run repetition gate

Before A acceptance and before B promotion, read connected units rather than grading them in isolation.

Challenge:

- `problem -> professional -> boundary -> useful action -> lesson`;
- evaluator fragments by habit;
- `Not X. Y.` reversals by habit;
- repeated joke placement;
- dialogue followed by an explanation of what it proved;
- tidy Greg-principle endings;
- uniformly reasonable supporting adults;
- work dominating selection because work is easy to generate;
- anti-escalation becoming a formula;
- compression that skips the promised lived scene;
- gap openings that mechanically list two time changes in the same order every chapter;
- every temporal checkpoint sounding like a ledger update.

Variance is diagnostic, not a quota.

## Re-performance

No low-confidence future wording receives sunk-cost protection.

When material approaches accepted authority:

1. fresh-read exact accepted R2 prose and Story State;
2. fresh-read relevant established people and relationships;
3. read the surviving future discovery and its time/constraint context;
4. discard assumptions invalidated by newer authority;
5. ask **WHAT SHOULD ACTUALLY HAPPEN NEXT?**;
6. re-stage at current Shared Greg Surface quality;
7. preserve old wording only where it still wins.

A surviving temporal clock or constraint is evidence about why the experiment worked. It does not automatically become canon.

## Survivor labels

- `SOURCE WIN` — still wins at current confidence;
- `REPERFORM` — core survives; rendering/scene must be fresh;
- `FORK` — multiple materially viable trajectories remain;
- `DISCOVERY ONLY` — event dies; useful pressure survives;
- `KILL` — no useful residue remains.

## Run storage and resumption

For a substantial temporal experiment:

1. create or use an isolated branch;
2. copy `TEMPORAL_RUN_TEMPLATE.md` into the experiment folder as `TEMPORAL_RUN.md`;
3. anchor it to current accepted authority;
4. resolve the clock;
5. resolve at least one constraint/nudge;
6. update only the current compact run state as the experiment moves;
7. keep prose/checkpoints separate from planning state;
8. on `continue`, read newest accepted authority, the branch's `TEMPORAL_RUN.md`, and the current experiment edge;
9. reconcile if accepted authority changed materially;
10. continue without asking the user to repeat already-durable instructions.

The run file is not canon. It is a resumable experiment contract.

## Default interpretation of the latest proven nudge set

The completed year experiment provides a useful calibration example, not permanent story truth.

A prompt equivalent to:

`a year, Gold party, more action, a little more tropes, continue`

should resolve approximately as:

```text
CLOCK: one year
HARD CONSTRAINT: a meaningful Gold-caliber party appears during the run
SOFT NUDGES: increase action pressure; permit somewhat more recognizable fantasy/isekai pleasure
CONTINUE: preserve the current run contract and current state unless a newer nudge changes it
WORD COUNT: fidelity target only unless explicitly hardened
AUTHORITY: current accepted R2 remains canon; this run remains speculative
```

The engine should not need a questionnaire to understand that instruction.

## North star

**CHARACTER BEFORE SYSTEM.**

**TIME MUST LEAVE RESIDUE.**

**SPECIFICITY BEFORE THESIS.**

**DISCOVERY BEFORE COMPETENCE DISPLAY.**

**UNRESOLVED PRESSURE BEFORE TIDY CLOSURE.**

**CURRENT PEOPLE BEFORE FUTURE KNOWLEDGE.**

**PLANNER KNOWS THE RUBRIC. RENDERER KNOWS THE SCENE.**

**LATER R2 IS QUARRY, NOT RAILROAD.**

The engine succeeds only if a deeper future backlog increases options, makes fictional time legible, and produces more life without making the accepted novel more predictable.
